## 苹果(pingguo)夹爪门禁问题 —— 根因定位与修复

**结论：苹果抓取几何本身是对的，错的是 lift 门禁阈值被硬编码成 0.85。**

### 夹爪反馈的真实物理含义（从官方 MJCF 推导 + 实测确认）

| 事实 | 来源 |
|---|---|
| 腱 `rgt_gripper_gear` = -12.5×左指 + 12.5×右指 | `mmk2_options.xml` |
| finger1/finger2 为对称 slide，各行程 0.04 m（总开口 0.08 m） | `airbot_play_dependencies.xml` |

## 苹果标定执行链 —— creep 阶段死锁（第二个独立缺陷）

**结论：苹果抓取除门禁阈值外，还有第二个独立缺陷——creep 停止判据在 L3 高层会死锁。**

### 现象

第一次跑 `run_pingguo_calibration.sh`：deploy 成功（`deploy=[0.90649, 3.05791, 1.214]`，IK 选 slide≈0.27），
但 creep 阶段 `base_y` 冻结在 2.709、`dist=0.141` 不再收敛，连续 55 次迭代（>100 s）无进展，最终 `CREEP 停止：超时，自动停车`。

### 根因（数值已验算）

`grasp_creep_controller.py` 有两个**互斥**的停止条件：

1. **名义 y 停止线**：`stop_y = object_center_y + creep_stop_dy` = `(3.243+0.0350)+0.035` = **3.313**，
   判据 `distance = stop_y - ee_world[1] <= y_tolerance (0.025)`。实测 `ee_y=3.171` → `dist=0.141`，差 116 mm。
2. **货架物理前沿**：`pickup_physical_stop_ready()` 要求 `front_min <= 0.40` 且 `0 < dist <= 0.10`。
   实测 `front` 恒在 **0.527~0.535**，永远不满足 0.40。

而底盘被货架挡住（`base_y` 卡在 2.709），既无法再前进满足条件 1，`front` 又降不到 0.40 满足条件 2 → **死锁**。

**为何可乐不复现**：kele 在 **L2**（z=0.9135），`stop_y=3.304`，`ee_y` 可达 3.247 → `dist=0.058` 直接满足。
苹果在 **L3**（z=1.224），货位更深，机械臂前伸够不到同等的 y 裕度。这是**层级高度导致的几何差异**，不是夹爪问题。

### 修复

creep 调用必须带 **`--object-stop-only`**：该开关令 `physical_front_stop = False`，
停止判据退化为纯物体几何（y 停止线），绕开不可达的货架前沿门禁。

```
python3 -u $BASELINE/grasp_creep_controller.py --execute --confirm creep \
  --object-stop-only --pickup-approach --speed 0.12 --timeout $CREEP_TIMEOUT
```

注意：`run_fixed_single_item_full.sh`（可乐脚本）**不带**这个开关，因为 L2 位置恰好两者都能满足。
苹果/L3 及更高层级必须带。⚠️ 这是脚本级差异，容易在复制脚本时漏掉。

## ⚠️ 第三个缺陷（最隐蔽）：Python 3.10 字节码缓存吞掉了源码修复

**现象**：`grasp_geometry.py` 已改成 `pingguo → 0.9188`，在容器内 `python3 -c "from grasp_geometry import ..."`
也打印 0.9188，但真实跑链时 `lift_controller` 始终报 `threshold=0.850`。

**根因**：`baseline/__pycache__/` 里存在 **`grasp_geometry.cpython-310.pyc`（9/9 19:46，即修复之前）**。
- 容器内 Python 是 **3.10.12**
- 宿主机（Windows）用的是 3.13，我在宿主机 `py_compile` 只生成/更新了 `cpython-313.pyc`
- baseline 以 `:ro` 挂载，**只阻止 Python 写新缓存，不阻止它读已有缓存**
- 于是容器加载了 9/9 的旧字节码 → 门禁仍是 0.85，修复形同不存在

**关键教训**：改完 `baseline/*.py` 后，**必须删除 `baseline/__pycache__/*.cpython-310.pyc`**，
否则容器会静默使用陈旧字节码。这是一类极难发现的"修复不生效"陷阱——
源码 grep 正确、容器内 import 正确，但真实执行走的是旧缓存。

> 注：容器内 `python3 -c "import"` 那次之所以显示 0.9188，是因为 cwd 落在 `/workspace/baseline`
> 之外、`sys.path` 指向的导入路径不同，未命中同一个 `__pycache__`。真实控制器以脚本方式
> 直接执行同目录模块，才会命中旧 `.pyc`。

**处置**：`rm -f baseline/__pycache__/*.cpython-310.pyc`（共 14 个），清后验证容器取值为 0.9188 / 0.9712 ✓

# ✅ 根因确认：WSL `vmIdleTimeout`（20:47–21:05）

## 真正的根因

**不是崩溃，是 WSL 主动关机。**

决定性证据来自 Docker daemon 日志（`journalctl -b -1 -u docker`）：

```
20:49:59  systemd[1]: Stopping Docker Application Container Engine...
20:49:59  dockerd: Processing signal 'terminated'      ← 收到 SIGTERM
20:50:02  dockerd: Daemon shutdown complete            ← 优雅关闭
20:50:02  docker.service: Deactivated successfully.
```

**机制**：`.wslconfig` 的 `vmIdleTimeout` 默认为 60000 ms。当**最后一个 `wsl.exe`
会话断开**后满 60 秒，WSL 判定 VM 空闲，直接关闭整台虚拟机，正在运行的仿真
连同所有容器一起被杀。之后重启时才会出现 `p9io.cpp:258 AcceptAsync` 与
`hv_balloon` 字样 —— 那些是**关机流程的产物，不是原因**。

**我踩的坑**：用 `setsid ... & disown` 启动仿真后立即返回，导致 `wsl.exe`
会话断开 → 60 秒后 WSL 自动关机。于是仿真"总是运行 30–60 秒后死掉"。

**为什么唯独 `pingguo_calib_console5.log` 那次成功？** 那次用的是
`run_in_background` 的后台阻塞方式，`wsl.exe` 进程**全程存活到脚本结束**，
WSL 自然不会被判为空闲。

## 正确做法（务必遵守）

跑长任务（仿真、构建、数据采集）时，**必须让 `wsl.exe` 会话存活**：

- 用 Bash 工具的 `run_in_background=true` 前台阻塞式调用，或
- 在命令末尾 `wait` 保持会话，**不要** `setsid ... & disown` 后立即返回

反例（会被 60 秒后杀掉）：
```bash
wsl.exe -d Ubuntu-22.04 -u root -- bash -c "setsid bash long_task.sh & disown; echo STARTED"
```
正例：
```bash
# run_in_background=true，wsl.exe 全程阻塞
wsl.exe -d Ubuntu-22.04 -u root -- bash -lc "bash /opt/jbgz/baseline/run_pingguo_hold.sh > log 2>&1"
```

# sanmingzhi 根因锁定：正面平面 + 深度过大 ⇒ 指头顶推（非参数问题）

## 决定性证据：位移方向分析

对基线遥测做逐帧位移分解：

```
首帧 position = (0.7000, 3.2430, 0.5484)     ← 与布局配置完全一致
x 方向最大位移 = +0.0408 m
y 方向最大位移 = +0.1224 m                   ← 主导
⇒ 商品被沿 Y（机器人前进方向）顶走 12.2 cm
```

**不是"夹歪"，而是夹爪指头没能滑到商品两侧，直接顶在正面把商品推走。**

## 为什么偏偏 sanmingzhi 会这样

按"被夹方向的宽度"排序对比：

| kind | 形状 | 被夹方向宽度 | 正面形态 | 结果 |
|---|---|---|---|---|
| kouxiangtang | cylinder | 49 mm | 曲面 | ✅ |
| pingguo | sphere | 70 mm | 曲面 | ✅ |
| chengzi | sphere | 74 mm | 曲面 | ✅ |
| heweidao | frustum | ~79 mm | 曲面（圆台） | ✅ |
| **sanmingzhi** | **mesh_prism** | **65 mm** | **平面** | ❌ |

**宽度不是决定因素**（chengzi 74 mm 比 sanmingzhi 65 mm 更宽却成功）。
真正的两个因素是：

1. **正面是平面** —— 球/圆柱/圆台的曲面会让指头顺滑地滑向两侧；
   平面则让指头直接顶住，形成推力而非夹力。
2. **y 向深度 100 mm（九类最深）** —— 指头行程有限，从正面够不到商品"腰部"，
   无法在两侧形成有效夹持面。

夹爪几何确认（`airbot_play_dependencies.xml`）：
`finger1/finger2` 均为 `axis='0 1 0'` 的 slide，行程 `±0.04` ⇒ 最大开口 0.08 m。
**开口够（65 < 80），问题在于接近姿态与商品正面形态的配合。**

# 🎯 第五轮突破：sanmingzhi 夹住了（22:32–22:40）

## 结果

```
SURFACE_TO_CENTER_FWD = 0.005
SCORE = 890.414   RISE = 42.19 mm   TILT = 1.891°   SHIFT = 6.35 mm
GRIP% = 24.0      REASON = SUCCESS
```

**得分 890.4，高于 kouxiangtang 的 874.73。** 商品被准确夹住并抬升 42 mm。

## 根因：配置参数错了 6.5 倍

原先写的 `surface_to_center_fwd = 0.0500`，**当初是按 y 向深度 0.1000 的一半估算的**
（`dimensions_m=(0.0650, 0.1000, 0.0988)`）。但对斜面商品，这个估法根本不成立。

从 MJCF mesh 顶点直接插值：

```
<mesh name="sanmingzhi_mesh" vertex="
    -0.0325 -0.0500 -0.0494      ← 底边左端
    -0.0325  0.0500 -0.0494      ← 底边右端
    -0.0325  0.0345  0.0494      ← 顶点（偏 y 正侧 0.0345，不居中）
    ... 同上 x=+0.0325 三个点"/>
```

三角形截面在 **yz 平面**（x 为拉伸方向，厚度 0.0650）。
机器人沿 +y 接近，遇到**斜面**（底边左端 → 顶点）。夹爪在商品中心高度（z=0）接触处：

```
z: -0.0494 → +0.0494   (跨度 0.0988)
y: -0.0500 → +0.0345   (跨度 0.0845)
t = (0-(-0.0494))/0.0988 = 0.5
y = -0.0500 + 0.5 × 0.0845 = -0.00775
```

**真实表面距仅 0.00775 m，配置却写了 0.0500。**

代入代价：
```
stop_y = 3.243 + 0.035 + 0.0500 = 3.328
实际需要 ≈ 3.243 - 0.00775     ≈ 3.235
差距 0.093 m ⇒ 夹爪停在商品前方 9.3 cm，够不到，只能一路顶推
```

## 我此前判断的更正

**我先前说"sanmingzhi 正面是平面所以顶推、属策略问题"—— 这个判断是错的**，
主人的直觉（"三明治应该是能夹住的"）才是对的。

实际是**参数配置错误**，仍属参数级问题。
教训：`dimensions_m` 是**包络尺寸**，不能简单地用某一维的一半当
`surface_to_center_fwd`；**必须看 mesh 的实际接触面**。

## 交叉验证：成功案例的 surface_to_center_fwd 都对应"真实前表面"

| kind | 值 | 实际含义 |
|---|---|---|
| kouxiangtang | 0.0245 | cylinder 半径 |
| pingguo | 0.0350 | 球半径 |
| chengzi | 0.0370 | 球半径 |
| heweidao | 0.0400 | frustum 中段半径 |
| **sanmingzhi** | **0.0050** | **斜面在中心高度的真实 y（原 0.0500 错误）** |

MJMCF 的 `<geom type="box" size="...">` 是**半尺寸**，而 `dimensions_m` 是**全尺寸**——
两者混用是这次踩坑的根源之一。

# 🎯 maidong 解决：预压最优曲线（09-11 00:02–00:05）

## 扫描结果（GRIP_CLOSE，越小越紧）

| GRIP_CLOSE | 得分 | 抬升 | 倾角 | 位移 | 判定 |
|---|---|---|---|---|---|
| 0.060 | -974.8 | 4.9 mm | 20.4° | 63.6 mm | ❌ 太松，滑 |
| **0.050** | **768.5** | **41.6 mm** | 8.6° | 52.3 mm | ✅ **SUCCESS** |
| 0.040 | -975.5 | 4.9 mm | 27.2° | 75.9 mm | ❌ 太紧，压歪挤出（倾角 27°） |

**已固化**：`grip_close=0.050, calibrated=True`（grasp_geometry.py）。

## 机制确认

- 闭爪是**位置控制**：grip_close=0.08（默认最紧档）时指头闭到「贴住表面」即停
  （开口 66.1 ≈ 直径 65，**零预压**）→ 摩擦上限 < 0.643 kg 重力 → 抬 4.8 mm 即滑
- 0.050：目标位置越过表面 → 产生预压 → 正压力↑ → 摩擦上限↑ → 撑住了
- 0.040：过压 → 商品被压歪挤出（倾角 27°）
- **经典预压倒 U 型曲线，两侧都是失败**

## 方法论沉淀

1. **「抬升量小 + 接触正常」≠ 需要调位姿参数** —— 先看质量：
   九类里最重的商品（0.643 kg）接触完美却只抬 4.8 mm，第一反应应是
   「夹持力 vs 重力」，而不是继续扫 DEPLOY_DZ/CREEP_*。
2. **grip_close 的语义已实测确认**：它是米制位置指令（发给
   /right_arm_forward_position_controller/commands），**越小越紧**；
   覆盖通道 = `SUPERMARKET_<KIND>_GRIP_CLOSE` 环境变量 →
   grasp_geometry.py → grasp_goal_meta → close_gripper。
3. 逐类标定的三类抓手现已齐全：`surface_to_center_fwd`（几何）、
   `grip_feedback_max`（门禁）、`grip_close`（预压）。

# zhijin 定案：三条抓取路线全部走通到技术边界（09-11 00:15–02:00）

主人问"能不能从上方抓"引出的俯抓路线，实现后连同侧抓、拨动，三条路的
技术边界全部探明。

## 路线 1：侧抓 —— 几何不可能

纸巾 172×85×88，任意方向最小平行对距 **85 mm** > 夹爪开口 **80 mm**。
俯抓/斜抓都不改变对距（刚体几何属性）。差 5 mm。

## 路线 2：拨动改朝向 —— 两层障碍

- **v2（面接触）**：偏移 +0.10 时指头与商品右缘重叠 26mm 条带，接触摩擦
  （商品面 1.0 × 指头面 4.0，MuJoCo 取 max=4.0）太大 → 指头面**粘住**商品
  **平移推走**（遥测实证：y 向 4.66/4.41 cm，x 几乎为零——粘着推不转）。
- **v3（临界擦角，单会话闭环）**：偏移降到指头只擦商品前缘一角 → **单次可转
  21–45°**（闭环确认，遥测新增 orientation_yaw_deg 字段）。但两个硬障碍：
  a) 矩形旋转投影：横向宽 = 172·cosθ+85·sinθ，θ=26° 时最大 ≈192，**须转满
     90° 才降到 85** —— 中途状态反而更难夹；
  b) 结构性问题：每轮重启 Server 会因 FIXED_BASELINE 重置场景（v2 实证：
     每轮首帧 yaw=0.000）。已实现 REUSE_SERVER 单会话闭环解决，但转满 90°
     需要的拨动次数多、商品同时被持续前推（三轮累计前移 15.7 cm）。

## 路线 3：俯抓咬棱 —— IK 不可达

两版姿态：
- Rx(180°)=diag(1,-1,-1)：只是倒置，指头长轴仍**水平**伸向商品，贴着顶棱
  擦过（遥测 0.6% 接触、位移 5.7 cm，NO_CONTACT）。
- **Ry(-90°)=[[0,0,-1],[0,1,0],[1,0,0]]**：指头长轴竖直向下、开合轴水平 ——
  正确的俯抓姿态。但 **IK 完全不可达**：dz=0.060/0.087/0.115 三高度全部
  NO_CONTACT，dz=0.087 日志 899 次"部署 IK 不可达"重试无解。
  ⇒ 竖直向下的工具姿态超出该 6 轴臂（airbot play）在 L2 货位前方的工作
  空间（大概率腕部关节限位）。

## 结论

**当前 80 mm 二指平行夹爪对 zhijin 无解**（差 5 mm 的几何鸿沟 × 机械臂
工作空间限制 × 拨转需满 90°）。可行出路（非软件参数层）：
1. 换装吸盘或更宽开口的末端执行器；
2. 专门的"拨转-对位"动作序列工程（需转满 90°+位置伺服，工程量大）；
3. 比赛策略上放弃该单品（8/9 的得分期望远高于死磕）。
